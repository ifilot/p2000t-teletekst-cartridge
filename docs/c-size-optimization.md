# C cartridge size optimization

This note records measurements from the linked SDCC image rather than source
line counts. Function boundaries come from the Z88DK map and compiler listing;
Raw LZ4 measurements use high-compression mode without a stored-size prefix,
matching `lz4_z80.asm`. Runtime startup measurements count emulated Z80
T-states, rather than host wall-clock time.

## Implemented compression

- The 960-byte opening-screen base is stored as a 383-byte raw-LZ4 block. The
  blinking prompt, countdown, and shared version footer remain overlays.
- The 341-byte error-description table is stored as a raw-LZ4 block.
- The complete 960-byte help screen is stored as a 402-byte raw-LZ4 block.
  This replaces its procedural drawing function and separate string literals.
  `display_screen` is reused as the decode buffer, so it consumes no additional
  RAM. Returning from help re-renders the raw page and its current markers.

Whole-screen templates are most useful when nearly every row is static. The
source menu, URL editor, network list, and error screens contain dynamic fields;
compressing those screens would require a base template plus overlays. That is
still a reasonable future optimization if another feature exhausts the ROM,
but it adds more generated byte arrays and should be driven by a measured need.

## Production ROM/RAM runtime split

The production build now uses **viewer-core with ZX0**. `make -C src` compiles
optimized viewer assembly, `prepare_runtime.py` places the core in a dedicated
RAM section, and a final link resolves all ROM/RAM calls at their real addresses.
The pinned toolchain compresses and independently decodes the RAM binary before
`make_cartridge_rom.py` validates and packages it. `runtime_loader.asm` unpacks
it before `main`, while interrupts are disabled.

The signed cartridge uses **14,069 ROM bytes**, leaving **2,315 bytes free**.
Its **5,255-byte RAM runtime** leaves **1,897 bytes for growth** after protecting
**1 KiB for the stack**. This supports **16 KiB total RAM**, including the
reserved monitor workspace. The selected policy is enforced by the normal
build, `make -C src verify`, and regression tests; it is not an optional build
flag. Actual linked sizes are recorded in `build/cartridge/measurements.json`.

`make -C src smoke` runs layout rejection tests and the complete emulator suite.
The emulator is configured with 16 KiB RAM; each scenario checks the whole
decoded runtime and untouched unused RAM below the protected stack region.
Early opening/scan snapshots allow for the one-time startup decompression.
Hardware boot and stack validation remain a useful release check.

The experimental builder and benchmark remain available for future comparisons.
Experiments copy sources into a new directory and do not change production
sources or the release image.

## Measured alternatives

Measured on 6 October 2026 with the pinned Z88DK 2.4 image and the existing
build-information header, the baseline payload is **16,361 bytes**, leaving
**23 bytes** in the 16 KiB cartridge. These are actual linked and packaged
sizes, including the loader, any additional decoder, initialized data, and
compressed-block metadata:

The current experiments assume **at most 16 KiB total RAM**, including
monitor workspace, mutable data and the stack. A **1,024-byte stack reserve**
is enforced by the builder. The earlier 32 KiB experiment is excluded from
both the available variants and the recommendations.

| Runtime selection | Codec | Decoded bytes | ROM used | ROM free | RAM growth after stack reserve | Startup to `main` |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| Baseline, all ROM | None | 0 | 16,361 | 23 | 7,213 | 34.0 ms |
| Viewer core | LZ4 | 5,255 | 14,905 | 1,479 | 1,897 | 115.9 ms |
| Viewer core | ZX0 | 5,255 | 14,069 | 2,315 | 1,897 | 226.8 ms |
| Viewer core | ZX7 standard | 5,255 | 14,338 | 2,046 | 1,897 | 295.4 ms |
| Viewer core | ZX7 turbo | 5,255 | 14,360 | 2,024 | 1,897 | 229.6 ms |
| Viewer core + plain strings | LZ4 | 5,825 | 14,784 | 1,600 | 1,327 | 123.6 ms |
| Viewer core + plain strings | ZX0 | 5,825 | 13,851 | 2,533 | 1,327 | 248.9 ms |
| Viewer core + protocol | ZX0 | 6,694 | 13,560 | 2,824 | 458 | 288.2 ms |
| Whole Teletekst module | ZX0 | 6,922 | 13,387 | 2,997 | 230 | 294.1 ms |

Startup times assume the emulator's 2.5 MHz CPU. They include normal CRT
initialization (34.0 ms at baseline), and exclude real hardware wait states
and monitor cartridge discovery/checksum time. Subtract 34.0 ms to estimate
added decompression cost. Figures describe CPU time, not build time or the
host's emulator execution speed.

The viewer-core selection includes every function from
`expected_status_length` through `teletekst_start`; settings, source selection,
custom URL entry and help handling remain in ROM. `core-protocol` additionally
moves all protocol functions. `core-strings` additionally moves 570 bytes of
compiler-generated string literals into the same decoded image, but leaves
compressed screen arrays and indicator data in ROM. Whole-module selection
moves all Teletekst functions and keeps their constants in ROM.

The two-function LZ4 experiment also remains reproducible with `fetch-viewer`:
it occupies 2,901 decoded RAM bytes, uses 15,663 ROM bytes and leaves 721 ROM
bytes free. Whole-module LZ4 uses 14,443 ROM bytes and leaves 1,941 bytes free;
its measured startup time is 144.6 ms.

### Performance interpretation

**Best startup speed:** viewer-core with LZ4. It adds about 81.9 ms to CRT
startup, versus 192.9 ms for viewer-core ZX0, but leaves 836 fewer ROM bytes.

**Most free ROM:** whole-module ZX0. It fits within 16 KiB RAM and preserves
the 1 KiB stack allowance, but leaves only 230 RAM bytes for future runtime or
buffer growth.

**Best balance for continued development:** viewer-core ZX0. It recovers
2,292 ROM bytes and leaves 1,897 RAM bytes for growth after the stack reserve.
Adding strings recovers a further 218 ROM bytes at a cost of 570 RAM bytes and
22.0 ms extra startup time. Adding the protocol recovers 509 more ROM bytes
but leaves only 458 RAM bytes for growth. The ZX7 variants are dominated by
ZX0 here: they offer less ROM capacity and slower startup with the same decoded
RAM footprint. Faster ZX0 turbo/fast decoders use self-modifying code; they
cannot simply replace the ROM-resident decoder and were not selected.

Once startup completes, the generated routines execute directly from RAM.
The sampled `clock_text` path took exactly **2,115 emulated T-states per call**
in the baseline and every measured layout (20 calls each). This confirms no
steady-state penalty for that path; it is not a timing proof for every feature
or a measurement of physical ROM/RAM wait states.

### Link and startup arrangement

Mutable data starts at `0x7000` and currently ends at `0x7fc3`. The runtime
starts at **`0x8000`**. A single link resolves calls and data references across
both ROM and RAM. The runtime's explicit origin makes Z88DK emit a separate
binary; it is not included verbatim in the resident ROM output.

The packer appends initialized DATA followed by the compressed runtime after
ROM code/constants. The loader computes that address from linker symbols.
LZ4 uses a two-byte compressed-size prefix and the existing decoder. ZX0 is
self-terminating and adds the toolchain's standard decoder. ZX7 offers standard
and turbo decoders; LZ4 stays resident
for the existing screen assets. Startup sets SP, initializes BSS/DATA, and
unpacks the runtime while interrupts are disabled, before calling `main`.
There is no runtime overlay, relocation pass or function-call trampoline.

Copying the existing ROM instructions to RAM is invalid because their absolute
addresses would be wrong. These builds instead link the runtime for its final
address **before** compression. Appending the packed bytes after linking avoids
a second link that might shift ROM references and invalidate the compressed
code. The builder checks the emitted layout, BSS/runtime overlap, at least
1 KiB of stack space, selected-function addresses, host decompression round-trip,
ROM capacity, and the cartridge checksum.

### RAM budget and verification

On the existing 16 KiB layout, SP starts at `0x9ff0`:

| Runtime selection | Runtime end, exclusive | Space below stack top |
| --- | --- | ---: |
| Two functions | `0x8b55` | 5,275 bytes |
| Viewer core | `0x9487` | 2,921 bytes |
| Whole module | `0x9b0a` | 1,254 bytes |

The whole-module LZ4 image passed the existing end-to-end assertions across
64 emulator executions, using an instrumented emulator with **16 KiB RAM**.
The early scan-screen capture moved from frame 10 to frame 13 to allow startup
decompression. Minimum observed SP was `0x9f05`: 235 bytes below stack top,
leaving 1,019 bytes clear of runtime code. Every execution also dumped the
runtime memory and verified that all decoded bytes still matched the linked
binary. This is an observed test-suite bound, not a proof of worst-case stack
usage on hardware.

The five new layouts (ZX7 standard/turbo, core+protocol ZX0, and core+strings
LZ4/ZX0) each passed seven targeted page, help, information, source-menu,
custom-URL, international-channel and fetch-error checks. Their complete RAM
runtime image was compared against the linked bytes after each execution.
All benchmarking uses an emulator explicitly configured with 16 KiB RAM.

The whole-module ZX0 image also passed the end-to-end assertions, across
72 emulator executions. Its opening snapshot moved from frame 10 to frame 30
and its scan snapshot from frame 10 to frame 21; all assertions were retained.
The extra executions come from the existing loop that finds the profile-save
prompt. Its minimum observed SP was also `0x9f05`, and the complete decoded
runtime remained intact after every execution.

The recommended viewer-core ZX0 layout additionally passed all end-to-end
assertions across **69 emulator executions**, with opening/scan captures at
frames 30/21 and all RAM bytes verified after each run. Its minimum observed
SP was `0x9f05`, also a 235-byte observed peak stack. The 1 KiB reserve remains
protected independently of this measured value.

ZX0 substantially improves ROM capacity but takes longer at startup; its early
screen snapshots need additional settling time. Both codecs unpack only once,
so ordinary navigation and network operations use the same generated code.
Real P2000T boot, memory compatibility, and stack validation remain necessary
before adopting an experimental image for release.

### Reproduction and recommendation

From the repository root, with Docker available:

```sh
python3 src/experiment_split_runtime.py \
  --output /tmp/p2000-viewer-core-zx0 \
  --variant viewer-core --codec zx0
```

`--output` must name a new directory. Other variants are `whole-viewer`,
`fetch-viewer`, `core-protocol` and `core-strings`; available codecs are `zx0`,
`zx7`, `zx7-turbo` and `lz4`. LZ4 requires the host `liblz4` shared library.
ZX0/ZX7 compression and independent host round-trips use tools already supplied
by the pinned Docker image. The builder
reuses the current build-information header when present so comparisons have
the same timestamp bytes, otherwise it generates a fresh one.

The experiment output includes `build/p2wp-cartridge.bin`, the complete link
map, the uncompressed RAM binary, and `build/measurements.json`. Production
builds use viewer-core ZX0 independently of these experiments.

To reproduce CPU measurements, the benchmark script builds an instrumented
copy of the emulator and runs the current production image plus each supplied
experiment:

```sh
python3 src/benchmark_split_runtime.py \
  /tmp/p2000-viewer-core-zx0 \
  --output /tmp/p2000-runtime-timings.json
```

The output file must be new. This needs the ordinary emulator build dependencies
(CMake, Ninja, SDL2 and libcurl). It checks successful fixture-page rendering,
stack usage, and the complete decoded RAM image, and reports raw T-states,
startup milliseconds, timing differences relative to production, and
clock-formatting cycles. The historical table above used the former fully
ROM-resident build as its baseline; the benchmark now compares against the
production viewer-core ZX0 image. Instrumentation stays in a temporary copy
of the emulator.

## Assembly candidates

The remaining large functions are state machines whose branches call many C
and platform helpers. Rewriting `fetch_page`, `viewer_loop`, or `scan_networks`
entirely in assembly would reduce maintainability for uncertain savings. Small,
stable primitives remain better candidates: fixed-layout formatting, byte
copies, screen transforms, CRC inner loops, and monitor/port access. The current
map contains no `sprintf`, `printf`, division, or multiplication runtime to
remove.
