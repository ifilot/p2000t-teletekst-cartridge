# C cartridge size optimization

This note records measurements from the linked SDCC image rather than source
line counts. Function boundaries come from the Z88DK map and compiler listing;
raw-LZ4 measurements use high-compression mode without a stored-size prefix,
matching `lz4_z80.asm`.

## Implemented compression

- The 560-byte opening mosaic is stored as a 259-byte raw-LZ4 block.
- The 341-byte error-description table is stored as a raw-LZ4 block.
- The complete 960-byte help screen is stored as a 418-byte raw-LZ4 block.
  This replaces its procedural drawing function and separate string literals.
  `display_screen` is reused as the decode buffer, so it consumes no additional
  RAM. Returning from help re-renders the raw page and its current markers.

Whole-screen templates are most useful when nearly every row is static. The
source menu, URL editor, network list, and error screens contain dynamic fields;
compressing those screens would require a base template plus overlays. That is
still a reasonable future optimization if another feature exhausts the ROM,
but it adds more generated byte arrays and should be driven by a measured need.

## Whole-function compression experiment

The current BSS ends near `0x7e0e` and the stack starts at `0x9ff0`, leaving
about 8.5 KiB for carefully bounded RAM code. Compressing selected linked
function ranges produced these gross figures:

| Function | Linked bytes | Raw LZ4 bytes | Gross ROM saving |
| --- | ---: | ---: | ---: |
| `fetch_page` | 1,427 | 987 | 440 |
| `viewer_loop` | 1,278 | 1,038 | 240 |
| `choose_source` | 520 | 431 | 89 |
| `scan_networks` | 670 | 598 | 72 |
| `choose_custom_url` | 422 | 365 | 57 |
| `select_subpage` | 294 | 238 | 56 |

Copying the existing ROM bytes to an arbitrary RAM address is **not valid**.
SDCC emits absolute calls, jumps, and data addresses. A deployable RAM routine
must therefore be linked for its final RAM address before it is compressed.

A safe implementation would require this two-stage build:

1. Move a candidate into a dedicated compiler/linker section.
2. Give that section a fixed origin above BSS and emit it as a separate binary.
3. Compress that binary and include the block in the ROM link.
4. Reserve the exact RAM range and decompress it after CRT data/BSS setup but
   before the first call.
5. Keep calls between ROM and RAM linked against their final absolute addresses.
6. Check section overlap, decoded size, ROM checksum, emulator behaviour, and
   real hardware on every build.

Z88DK's assembler supports separate binaries for sections with their own
`ORG`, so the layout is technically feasible. It is not currently selected for
production: the best candidate saves at most roughly 400 bytes after loader
overhead, consumes 1.4 KiB of RAM, complicates the build, and puts the most
important fetch state machine outside immutable ROM. The existing LZ4 decoder
removes most decoder overhead, but not the relocation and build-system costs.
Revisit this only if a future feature cannot fit after static-screen
compression.

## Assembly candidates

The remaining large functions are state machines whose branches call many C
and platform helpers. Rewriting `fetch_page`, `viewer_loop`, or `scan_networks`
entirely in assembly would reduce maintainability for uncertain savings. Small,
stable primitives remain better candidates: fixed-layout formatting, byte
copies, screen transforms, CRC inner loops, and monitor/port access. The current
map contains no `sprintf`, `printf`, division, or multiplication runtime to
remove.
